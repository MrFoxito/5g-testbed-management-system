REPORTE DE IMPLEMENTACION - SECUENCIA E2E TIPO SMARTCARE
Fecha: 2026-09-05

OBJETIVO
Mejorar la visualizacion de las trazas extremo a extremo del EMS educativo tomando
como referencia funcional el archivo local flowchart.txt de SmartCare, sin copiar
codigo, clases CSS, marcas ni recursos propietarios del producto comercial.

ANALISIS DE LA REFERENCIA
- Se reviso el archivo traza smartcare/flowchart.txt.
- La referencia usa una composicion HTML basada en elementos sweet-* y capas div
  posicionadas, con columna temporal, cabeceras de nodos, lifelines, flechas y un
  panel de detalle sincronizado.
- Se identifico como patron util la navegacion bidireccional entre mensaje y
  evidencia: al seleccionar una flecha se presenta timestamp, enlace, extremos,
  protocolo y decodificacion.
- No se reutilizo el HTML, JavaScript, CSS, nombres de clases ni branding de Huawei.

IMPLEMENTACION PROPIA
- Se reconstruyo SequenceDiagram con React, TypeScript y SVG.
- Columna de timestamps fija durante el desplazamiento horizontal.
- Cabecera de funciones de red fija durante el desplazamiento vertical.
- Lifelines solidas y una fila temporal por evento.
- Flechas direccionales con color semantico por familia de protocolo:
  NAS, NGAP/S1AP, HTTP2/SBI, PFCP/N4, GTP-U/N3, GTP-C, ICMP y errores.
- Etiquetas de mensaje seleccionables y soporte de teclado mediante Enter/Espacio.
- Resaltado sincronizado entre la fila temporal, la flecha y el panel de detalle.
- Diferenciacion visual de eventos obtenidos directamente de PCAP/log/runtime y
  eventos correlacionados o inferidos.
- Filtros por senalizacion 3GPP, procedimiento y busqueda textual.
- Controles de zoom, densidad compacta, reinicio y salto al primer/ultimo evento.
- Leyenda de protocolos y explicacion de la linea discontinua.

PANEL DE EVIDENCIA
- Se amplio el panel del mensaje seleccionado con una disposicion operativa:
  timestamp, enlace, origen, destino, procedimiento, estado y numero de frame.
- Se muestran los identificadores correlacionados disponibles, por ejemplo SUPI,
  RAN UE NGAP ID, AMF UE NGAP ID, PDU Session ID y PFCP SEID.
- Se agrego una consola expandible con la evidencia de decodificacion disponible.
- El visor usa la evidencia real entregada por el backend; no genera mensajes de
  protocolo ficticios para completar visualmente la secuencia.

VALIDACION REALIZADA
- Compilacion TypeScript/Vite satisfactoria con pnpm run build.
- ESLint satisfactorio para los dos componentes modificados.
- Suite del backend satisfactoria: 21 pruebas aprobadas.
- Prueba visual automatizada contra frontend http://127.0.0.1:5173 y backend
  http://127.0.0.1:8000 usando la tarea real "Validacion manual E2E".
- La tarea mostro 109 eventos analizados; 103 resultaron visibles con el filtro
  inicial de senalizacion 3GPP.
- Se verifico la seleccion programatica de una flecha y la actualizacion del panel
  con el evento "InitialUEMessage, Registration request".

RESULTADO
El EMS dispone ahora de una secuencia E2E interactiva con presentacion comparable
al patron de herramientas telco comerciales, pero implementada de forma original
y orientada al aprendizaje: cada mensaje se relaciona con el procedimiento 3GPP,
los nodos participantes, los identificadores de sesion y la evidencia capturada.

AJUSTE DE JERARQUIA VISUAL
- Se eliminaron las cuatro tarjetas superiores de modalidad, duracion, evidencia y
  correlacion, reemplazandolas por una unica barra compacta.
- La cadena de identificadores ahora aparece plegada inicialmente y conserva un
  resumen con SUPI/IMSI, cantidad de identificadores y estado de correlacion.
- Se elimino el boton duplicado "Volver a Trazas" de la cabecera exterior.
- La secuencia E2E queda visible en el primer viewport sin perder informacion.
- Captura: reportes/2026-09-05_traza_vista_compacta.png

ACLARACION DE ESTADOS Y EVENTOS VACIOS
- "Completada" se cambio a "Captura finalizada" para separar el estado tecnico
  de la captura del resultado del procedimiento 3GPP.
- "No concluyente" se cambio a "Procedimiento no verificado".
- Cuando un filtro como Registro no contiene eventos, el diagrama explica que el
  procedimiento no fue ejecutado o no estuvo visible y que esto no implica exito.
- El estado de correlacion ahora se rotula explicitamente como "IDs" para evitar
  confundir una cadena de identificadores completa con un procedimiento exitoso.
- Se corrigio el mapeo semantico de trafico SBI: una direccion loopback ambigua ya
  no puede presentarse como gNodeB frente al NRF; se identifica como "5GC NF".

CORRECCION DEL REGISTRATION REAL
- Se ingreso por SSH al testbed y se comprobo que Open5GS, gNodeB y UE estaban
  activos. Un reinicio manual del servicio UERANSIM genero correctamente
  Registration, 5G-AKA y PDU Session Establishment.
- La causa de las trazas inconclusas era que "Disparar procedimiento" iniciaba
  desactivado; el UE permanecia registrado y solo se capturaba trafico periodico.
- El formulario ahora activa por defecto el reinicio controlado para docentes,
  desactiva SBI por defecto y reduce la duracion inicial a 60 segundos.
- El backend espera que tshark este listo antes del reinicio y verifica mediante
  nr-cli que el UE alcance RM-REGISTERED y CM-CONNECTED.
- Los marcadores del journal se limitan a la ventana de la tarea para no atribuir
  exitos antiguos a capturas nuevas.
- El exito del procedimiento se separo de la completitud de identificadores.
- Se limpiaron prefijos SCTP/SACK de las etiquetas NGAP/NAS y se ocultan por
  defecto heartbeats Nnrf, DATA y respuestas HTTP 204 de mantenimiento.
- Validacion E2E final: tarea 09fee975bb164ef2aadb63e4ec52c882, 40 paquetes,
  21 eventos, IMSI confirmado, Registration exitoso, 5G-AKA exitoso y PDU Session
  exitosa.
