REPORTE DIARIO DE AVANCE
Fecha local: 02 de septiembre de 2026
Proyecto: EMS educativo multi-VM para laboratorios 4G/5G

1. DECISIONES DE ALCANCE

- Se redefinió el proyecto como una plataforma web educativa inspirada en EMS/FCAPS.
- Se eliminó la afirmación de que el producto será carrier-grade o equivalente a plataformas comerciales.
- Se estableció que el EMS gestionará testbeds previamente instalados; no creará máquinas virtuales ni reemplazará el Módulo 2 de OpenStack/Heat.
- Se conservaron dos arquitecturas principales: 4G EPC y 5G Standalone.
- Se redujo la arquitectura lógica de once módulos a siete módulos integrados.
- Se conservaron OpenTelemetry y OpenObserve como extensión avanzada, sin convertirlos en requisito mínimo de aprobación.
- Se decidió utilizar shadcn-admin como base del frontend y FastAPI como backend.
- Se definieron casos experimentales propios basados en los Laboratorios 3 y 4, sin reutilizar la nomenclatura E1-E4 del proyecto OM_module.
- Se acordó citar OM_module como trabajo relacionado y presentar nuestra plataforma como una contribución complementaria orientada a gestión educativa multi-VM.

2. PLAN DE IMPLEMENTACIÓN

- Se reescribió IMPLEMENTATION_PLAN.md con el nuevo enfoque.
- El sistema quedó organizado en los siguientes siete módulos:
  1. Inventory & Topology.
  2. Execution & Control Gateway.
  3. Health, Alarms & Logs.
  4. Trace Studio.
  5. Configuration & Subscribers.
  6. Dashboard & KPIs.
  7. Evidence & Audit.
- Se reorganizó el desarrollo en seis sprints.
- Se definieron requisitos no negociables, extensiones de alto valor y un orden explícito de recorte.
- Se definieron criterios de aceptación y una secuencia objetivo para la demostración final.

3. PREPARACIÓN DEL TESTBED LOCAL

- Se creó y configuró una VM VirtualBox con Ubuntu Server 22.04.5 LTS.
- Se habilitó OpenSSH y el acceso desde Windows mediante red NAT y reenvío del puerto local 2222 hacia el puerto 22 de la VM.
- Se instaló y validó MongoDB 7.0.42.
- Se instaló Open5GS 2.8.0 para Ubuntu Jammy.
- Se compiló e instaló UERANSIM 3.3.0.
- Se creó el script infra/configure_5g_sa_lab.sh para preparar el escenario educativo 5G SA.
- Se configuraron servicios systemd para la red del laboratorio, gNodeB y UE de UERANSIM.
- Se configuraron forwarding, NAT y el túnel ogstun.
- Se añadió un suscriptor de laboratorio compatible con UERANSIM.
- Se validó previamente el registro 5G, el establecimiento de PDU Session y conectividad IP desde el namespace del UE.

4. REFACTORIZACIÓN DEL BACKEND

- El catálogo de escenarios dejó de estar hardcodeado en Python.
- Se creó backend/app/catalog/scenarios.json como inventario declarativo 4G/5G.
- Se creó backend/app/catalog/mock_states.json para separar los datos simulados del código.
- Se creó backend/app/services/catalog.py para cargar y validar el catálogo.
- El validador comprueba identificadores duplicados, nodos inexistentes y dependencias inválidas.
- Cada función de red ahora declara:
  - nodo o VM donde se ejecuta;
  - unidad systemd;
  - tipo de componente;
  - interfaces telco;
  - dependencias.
- Se añadieron al dominio los campos node_id e interfaces.
- El estado transitorio deploying se cambió por starting para coincidir con el nuevo plan.
- Se mantuvieron los adaptadores simulated, local y remote.
- SimulatedExecutionAdapter ahora carga su estado desde JSON.
- RemoteExecutionAdapter quedó configurado para consultar la VM por SSH.
- Se añadió un snapshot de runtime que obtiene hostname, interfaces, direcciones, MTU y sockets en escucha.
- Se añadió el endpoint GET /api/v1/runtime/{scenario_id}.
- Se optimizó la consulta de servicios: todos los estados de un escenario se obtienen con una sola operación systemctl por ciclo, en lugar de abrir una conexión SSH por cada NF.
- Se normalizó la salida de systemctl para traducir estados de Linux a running, stopped, degraded o unknown.
- Se añadió SCP al inventario 5G porque el servicio está realmente instalado y activo en la VM.
- No se añadieron BSF ni SEPP al escenario base porque actualmente no participan en los procedimientos educativos seleccionados.

La consola ya obtiene por SSH el estado real de Open5GS y UERANSIM desde la VM Ubuntu, conoce las funciones de red y sus interfaces 3GPP mediante un inventario declarativo, y presenta información del testbed sin depender todavía del VNRT ni de OpenObserve.

11. ACTUALIZACIÓN: TOPOLOGÍA Y SALUD TELCO

- Se crearon dos modos de topología: vista física y vista telco.
- La vista física representa honestamente la VM local combinada y muestra hostname, IP, interfaces Linux y cantidad de NFs alojadas.
- La vista telco representa funciones de red, dependencias e interfaces 3GPP.
- Los nodos pueden moverse y mantienen su posición durante las actualizaciones.
- Al seleccionar una NF se abre un panel con servicio systemd, nodo, interfaces, procedimientos, dependencias, configuraciones, endpoints y logs reales.
- Se añadieron perfiles declarativos para las principales NFs 4G/5G.
- Se incorporaron endpoints esperados TCP, UDP y SCTP para MongoDB, SBI, N2, N3 y N4.
- El runtime remoto ahora incluye sockets SCTP además de TCP y UDP.
- Se implementaron health checks de servicios y endpoints.
- Para 5G también se verifica evidencia real de NG Setup, Registration y PDU Session en logs de UERANSIM.
- Las alarmas incluyen NF, nodo, interfaz, procedimiento, causa probable, evidencia y recomendación.
- La página de alarmas fue rediseñada para mostrar el contexto telco.
- Se añadieron acciones de inicio y detención por NF, restringidas por rol, confirmadas por el usuario y registradas en auditoría.
- El escenario saludable fue validado con 13/13 componentes activos, 59 endpoints detectados, logs del AMF accesibles y cero alarmas activas.
- Las pruebas automatizadas aumentaron a 8 y todas aprobaron.
- ESLint, compilación TypeScript/Vite y compilación Python aprobaron.

12. ACTUALIZACIÓN: TRACE STUDIO REAL

- Se comprobó que dumpcap ya tenía capacidades cap_net_admin y cap_net_raw.
- Se añadió emsadmin al grupo wireshark para permitir capturas sin ejecutar el backend como root.
- Se creó infra/configure_tshark_permissions.sh para reproducir la configuración de permisos.
- tshark detecta las interfaces enp0s3, ogstun, any y lo.
- Se definieron puntos 5G N2, N3, N4, N6 y SBI con filtros internos.
- Se definieron puntos 4G S1-MME, S1-U, S11, S6a y SGi.
- Se implementó inicio remoto de tshark con límites obligatorios de duración y tamaño.
- Se implementaron consulta de estado, detención controlada y transferencia SFTP del PCAP.
- Los metadatos de las capturas se persisten en backend/data/captures/metadata.json.
- El resumen remoto obtiene cantidad de paquetes, tamaño y distribución por protocolo.
- Trace Studio permite seleccionar tecnología, punto de referencia, duración y tamaño máximo.
- La tabla muestra capturas activas/completadas, protocolo, interfaz, paquetes, tamaño y origen.
- Se implementó descarga autenticada del PCAP desde el navegador.
- Se añadió backend/tests/manual_remote_trace.py como prueba de integración reproducible.
- Se validó una captura N6 real generando ping desde el namespace del UE.
- Resultado: PCAP completado de 1064 bytes con 6 paquetes ICMP, transferido y descargado correctamente mediante HTTP 200.
