> [!IMPORTANT]
> **¿Por qué separar SGW-U y PGW-U en 2 VMs?** En la arquitectura CUPS (3GPP TS 23.214), el SGW-U maneja el tráfico S1-U (entre eNodeB y el core) y el S5/S8-U (hacia el PGW-U), mientras que el PGW-U da salida al Internet (interfaz SGi). Separarlos permite:
> - Medir el consumo de recursos de cada plano de usuario por separado.
> - Estudiar qué pasa cuando cae el SGW-U vs. el PGW-U.
> - Demostrar visualmente la arquitectura CUPS del EPC en la topología del EMS.

## Detalle de Cada VM

### VM 1: `EMS-EPC-CP` — Plano de Control (`10.210.40.1`, SSH 2230)

Aloja todas las funciones del plano de control del EPC, más MongoDB:

| Servicio | Demonio systemd | Interfaces/Protocolos | Escucha en |
|----------|-----------------|----------------------|------------|
| MongoDB | `mongod` | TCP 27017 | `127.0.0.1:27017` |
| HSS | `open5gs-hssd` | Diameter S6a | `127.0.0.1:3868` |
| PCRF | `open5gs-pcrfd` | Diameter Gx | `127.0.0.1:3869` |
| MME | `open5gs-mmed` | S1-MME (SCTP), S11 (GTPv2-C), S6a | `10.210.40.1:36412` (SCTP), `10.210.40.1:2123` (S11) |
| SGW-C | `open5gs-sgwcd` | S11 (GTPv2-C), S5-C (GTPv2-C) | `10.210.40.1:2123` (S11), `10.210.40.1:2123` (S5-C) |
| PGW-C/SMF | `open5gs-smfd` | S5-C (GTPv2-C), Gx, PFCP (N4) | `10.210.40.1:8805` (PFCP hacia PGW-U) |

> [!NOTE]
> Open5GS implementa CUPS nativamente: el `smf` actúa como PGW-C y controla al `upf` (PGW-U) mediante PFCP. El `sgwc` controla al `sgwu` también por GTP-C/PFCP. Esto hace posible la separación sin parches.

### VM 2: `EMS-SGW-U` — Serving Gateway User Plane (`10.210.40.2`, SSH 2231)

| Servicio | Demonio systemd | Interfaces | Escucha en |
|----------|-----------------|------------|------------|
| SGW-U | `open5gs-sgwud` | S1-U (GTP-U desde eNB), S5/S8-U (GTP-U hacia PGW-U), PFCP (desde SGW-C) | `10.210.40.2:2152` (GTP-U), `10.210.40.2:8805` (PFCP) |

- Recibe el tráfico del eNodeB por S1-U y lo envía al PGW-U por S5/S8-U.
- No necesita `ogstun` ni NAT; solo tuneliza GTP-U.

### VM 3: `EMS-PGW-U` — PDN Gateway User Plane (`10.210.40.3`, SSH 2232)

| Servicio | Demonio systemd | Interfaces | Escucha en |
|----------|-----------------|------------|------------|
| PGW-U/UPF | `open5gs-upfd` | S5/S8-U (GTP-U desde SGW-U), SGi (salida Internet), PFCP (desde PGW-C/SMF) | `10.210.40.3:2152` (GTP-U), `10.210.40.3:8805` (PFCP) |

- Interfaz `ogstun` con IP `10.44.0.1/16` (pool de UEs 4G).
- NAT Masquerade para dar salida a Internet.
- Análogo directo al `EMS-UPF-01` de Miguel.

### VM 4: `EMS-ENB` — eNodeB srsRAN (`10.210.40.10`, SSH 2233)

| Servicio | Demonio systemd | Interfaces | Escucha en |
|----------|-----------------|------------|------------|
| eNodeB | `srsenb` (o systemd custom) | S1-MME (SCTP hacia MME), S1-U (GTP-U hacia SGW-U), LTE-Uu (ZMQ hacia UE) | `10.210.40.10` |

- Usa **srsRAN 4G** (no UERANSIM).
- Comunicación radio con el UE mediante **ZeroMQ (ZMQ)** — enlace software sin necesidad de SDR.
- Archivo de configuración: `/etc/srsran/enb.conf`.

### VM 5: `EMS-UE-4G` — UE LTE (`10.210.40.11`, SSH 2234)

| Servicio | Demonio systemd | Interfaces |
|----------|-----------------|------------|
| UE | `srsue` (o systemd custom) | LTE-Uu (ZMQ hacia eNB) |

- Simula un terminal LTE.
- Al hacer Attach exitoso, crea la interfaz `tun_srsue` con una IP del pool `10.44.0.x`.
- Archivo de configuración: `/etc/srsran/ue.conf`.

### 4. Ejecución Remota — Extender `RemoteExecutionAdapter` en `execution.py`

#### [MODIFY] [execution.py](file:///c:/Users/Sergio/Desktop/TESIS_REPOSITORIO/5g-testbed-management-system/backend/app/services/execution.py)

El método [`_port_for_unit()`](file:///c:/Users/Sergio/Desktop/TESIS_REPOSITORIO/5g-testbed-management-system/backend/app/services/execution.py#L324-L333) actualmente solo conoce las unidades 5G. Se debe extender para rutear correctamente las unidades 4G:

```python
def _port_for_unit(self, unit: str) -> int:
    # 5G (existente)
    if unit in ("open5gs-upfd2", "open5gs-upfd-2"):
        return getattr(self.settings, "upf2_ssh_port", 2224)
    if unit == "open5gs-upfd":
        return getattr(self.settings, "upf_ssh_port", 2223)
    if unit == "ueransim-gnb":
        return getattr(self.settings, "gnb_ssh_port", 2225)
    if unit == "ueransim-ue":
        return getattr(self.settings, "ue_ssh_port", 2226)
    # 4G (nuevo)
    if unit == "open5gs-sgwud":
        return getattr(self.settings, "sgwu_ssh_port", 2231)
    if unit == "open5gs-upfd-4g":  # alias para PGW-U 4G
        return getattr(self.settings, "pgwu_ssh_port", 2232)
    if unit == "srsenb":
        return getattr(self.settings, "enb_ssh_port", 2233)
    if unit == "srsue":
        return getattr(self.settings, "ue4g_ssh_port", 2234)
    return self.settings.ssh_port
```

> [!WARNING]
> **Conflicto crítico con `open5gs-upfd`**: En 5G, `open5gs-upfd` se rutea al puerto 2223 (UPF-01). En 4G, el PGW-U también usa `open5gs-upfd`. Necesitamos un mecanismo para distinguir por **escenario**, no solo por unidad. Opciones:
> 1. Usar un alias como `open5gs-upfd-4g` en el catálogo 4G y mapearlo en `_remote_unit_name()`.
> 2. Pasar el `scenario_id` al adapter para resolver el puerto correcto.
> 
> **Recomendación**: Opción 2 — pasar `scenario_id` al método `_port_for_unit()` y tener un diccionario de mapeo por escenario.

## Open Questions

> [!IMPORTANT]
> **Pregunta 1: ¿Tienes acceso a la ISO de Ubuntu Server 22.04.5 que usó Miguel?**
> Miguel usó la ISO con SHA-256 `9bc6028870aef3f74f4e16b900008179e78b130e6b0b9a140635434a46aa98b0`. Necesitas la misma ISO o una compatible para crear tus VMs base y mantener consistencia de paquetes.

> [!IMPORTANT]
> **Pregunta 2: ¿Usarás `srsRAN Project` (antes `srsLTE`) o `srsRAN 4G`?**
> - **srsRAN 4G** (rama `release_23_11`): Solo LTE, más estable y maduro.
> - **srsRAN Project** (5G NR + LTE): Más pesado, orientado a 5G.
> 
> Para tu tesis 4G pura, **srsRAN 4G** es la opción correcta.

> [!IMPORTANT]
> **Pregunta 3: ¿Quieres que la comunicación eNB↔UE sea por ZMQ o por loopback?**
> - **ZMQ entre VMs**: Más realista (tráfico cruzando la red virtual), pero requiere compilar srsRAN con soporte ZMQ.
> - **ZMQ en la misma VM**: Más simple, pero pierde el beneficio de tener VMs separadas.
> - **Recomendación**: ZMQ entre VMs separadas (`EMS-ENB` y `EMS-UE-4G`), con `tx_port` y `rx_port` apuntando entre las IPs `10.210.40.10` y `10.210.40.11`.

> [!WARNING]
> **Pregunta 4: Conflicto de unidades `open5gs-upfd` entre escenarios.**
> El PGW-U de 4G y el UPF de 5G usan el mismo nombre de demonio (`open5gs-upfd`). ¿Prefieres:
> - **(A)** Resolver por escenario pasando `scenario_id` al `RemoteExecutionAdapter` — más limpio.
> - **(B)** Usar un alias en el catálogo (`open5gs-upfd-4g`) con mapeo en `_remote_unit_name()` — más rápido de implementar.
